0 · 先建立正确的模型 dnf 在做什么，仓库的本质是什么

大多数人对包管理的理解停在「下载 + 安装」。那样记命令，配仓库时必然靠试。先把下面这条链记住，后面每一步都能自己解释。

① 读 .repo→ ② 取 repodata→ ③ 解依赖→ ④ 下载 rpm→ ⑤ 校验签名 + 事务
步骤它实际在做什么失败时你会看到对应的验证手段
①读 /etc/yum.repos.d/*.repo + /etc/dnf/dnf.conf仓库根本没出现dnf repolist --all
②按 baseurl 取 repodata/repomd.xmlCannot download repomd.xmldnf makecache
③在元数据里算出「还要装哪些包」nothing provides ...dnf provides */命令
④下载 .rpm 到 /var/cache/dnf/Curl error / 超时看 /var/log/dnf.log
⑤GPG 校验、执行 rpm 事务GPG key ... NOT OKrpm -qa | grep 包名
本域最重要的一句话：仓库的核心不是 rpm 文件，是 repodata。
把 100 个 rpm 拷进 /opt/myrepo/，再写一个 baseurl=file:///opt/myrepo 的 .repo，dnf 一个包都看不见——因为那个目录里没有 repodata/。这就是 createrepo_c 存在的唯一理由：把 rpm 扫一遍，生成索引。
两个变量，看懂 .repo 的前提
$releasever：系统大版本号（Rocky 9 → 9），来自 system-release(releasever) 这个 provides。
$basearch：CPU 架构（x86_64）。
写成 .../rockylinux/$releasever/BaseOS/$basearch/os/ 就是为了「换机器不用改文件」。

1 · 看清现状 先只读，一个字节都不要改

ls + repolist
ls -l /etc/yum.repos.d/
dnf repolist
dnf repolist --all
成功长什么样：repolist 列出启用的仓库（id / name / status 三列）；--all 多出 disabled 的行。
文件数 ≠ 仓库数：一个 .repo 文件里可以有多个 [section]，每个方括号就是一个仓库。dnf repoinfo <id> 会告诉你它来自哪个文件第几行。
repoinfo / cat
dnf repoinfo baseos
cat /etc/yum.repos.d/*.repo
成功长什么样：看到 Repo-baseurl（变量已展开成真实 URL）、Repo-filename、Repo-expire。
dnf repolist 是会骗人的命令（你的老账本第 1 条）：它读的是 /var/cache/dnf/ 里的本地缓存，不联网。网络断了、baseurl 已经 404，它照样给你列出两行漂亮的仓库。它只证明「配置读通了」，不证明「仓库可用」。
clean + makecache
dnf clean all
dnf makecache
成功长什么样：结尾是 Metadata cache created.，每个启用的仓库一行，没有 error / Curl error。
为什么这条才算数：clean all 把本地缓存清空，makecache 被迫真的去 baseurl 拉一次 repodata。这是唯一能证明「仓库活着」的最小动作。
Repo-expire 里的 21600 是哪来的：.repo 里写的是 metadata_expire=6h，dnf 内部换算成秒：6 × 3600 = 21600。配置文件里给人看，输出里给机器看——所以 grep 21600 在文件里一个都找不到。
单位：d 天 / h 小时 / m 分 / s 秒，不写单位默认按秒。想让元数据 1 小时过期就写 metadata_expire=1h。
注意它不是「还剩多久过期」，而是「有效期长度」；后面括号里的 last: 才是上次刷新时间，两者相加才是下次过期时刻。
不同仓库可以不同：rocky 系列是 6h，epel 是 14d（=1209600s），不写则用 dnf 默认值。
--enablerepo / --disablerepo
dnf --disablerepo='*' --enablerepo=appstream list available | head
dnf --disablerepo=appstream repolist
成功长什么样：第一条只从 appstream 列包；第二条里 appstream 消失。
为什么要会这个：考试里经常要「只从这个仓库装」，改配置文件既慢又有风险。命令行参数的优先级高于 .repo 里的 enabled=，且只在这一次生效。

2 · 配一个本地仓库（file://）本域最常考的一题，也是唯一需要「造」的动作

目标：把一个装满 rpm 的目录变成一个 dnf 能识别的仓库，并只从这个仓库装一个包。顺序不能颠倒：先有 rpm → 再生成 repodata → 最后才写 .repo。

两条来源任选
# 路线 A：手上有 ISO / 安装光盘
mount /dev/sr0 /mnt
ls /mnt/BaseOS/Packages | head

# 路线 B：没有 ISO，从现有远程仓库下载几个包
mkdir -p /opt/localrepo
dnf download --destdir=/opt/localrepo tree htop lsof
成功长什么样：/opt/localrepo/ 里出现若干 .rpm（路线 B）；或 /mnt/BaseOS/Packages/ 下有上百个 rpm（路线 A）。
为什么要拷贝出来：createrepo_c 要往目录里写 repodata/，光盘是只读的。所以要么把整个 Packages 拷到可写目录，要么把 ISO 挂载后 cp -r 出来。
createrepo_c
dnf install -y createrepo_c
createrepo_c /opt/localrepo
ls /opt/localrepo/repodata/
成功长什么样：createrepo_c 打印 Working environment ... Saving Primary metadata ... 之类；repodata/ 里有 repomd.xml、primary.xml.gz、filelists.xml.gz。
没有 repomd.xml 就等于没做：dnf 只认这个文件。看到 repodata/ 目录存在但里面是空的，说明 createrepo_c 中途失败了，重跑一次看报错。
什么时候要重跑：往目录里加了新 rpm，必须再执行一次 createrepo_c --update /opt/localrepo，否则新包在索引里不存在。
五个字段
vi /etc/yum.repos.d/local.repo
[local]
name=Local Repo
baseurl=file:///opt/localrepo
enabled=1
gpgcheck=0

cat /etc/yum.repos.d/local.repo
成功长什么样：五个字段齐全；baseurl 是 file:// + 三个斜杠（前两个是协议，第三个是根目录）。
file:// 后面必须三个斜杠：file:///opt/localrepo 对，file://opt/localrepo 会被当成主机名 opt。
gpgcheck=0 的取舍：自建仓库通常没有签名，关掉是最快的路；但生产上应导入 GPG key 并保持 gpgcheck=1。考试按题干要求写，没要求就 0。
字段名拼错不会报错：写成 enable=1（少个 d），dnf 照样跑，因为 dnf 不校验未知键，而 enabled 的默认值就是 1，恰好蒙对了。
危险的是反方向：想关掉却写 enable=0——这个键被忽略、默认仍是 1，仓库照样开着，屏幕上没有任何提示。
所以验证只能看 dnf repoinfo local 里的 Repo-status: enabled / disabled，不能靠「命令没报错」。
唯一算数的验收
dnf clean all
dnf --disablerepo='*' --enablerepo=local repolist
dnf --disablerepo='*' --enablerepo=local list available
成功长什么样：repolist 里只剩 local 一个仓库，status 是包数量而不是 0；list available 能列出你放进去的包名。
只看 repolist 会骗你：仓库能列出来，但 status 是 0，就说明 repodata 是空的或者包没进去。必须看到包名才算过。
--disablerepo='*'
dnf --disablerepo='*' --enablerepo=local install -y tree
rpm -qa | grep tree
成功长什么样：输出里 Installing: tree-...，且 Repository: local；rpm -qa 能查到。

为什么要 --disablerepo='*'：不加的话，dnf 会优先从网络仓库拿——那样你根本证明不了本地仓库起作用了。把其它仓库都关掉，剩下的结果才归因明确。

如果显示 already installed：说明这个包本来就在系统里（tree 很常见），dnf 不会重装，直接 Nothing to do。想练「真的从某个仓库装」，要么换一个没装的包，要么先 dnf remove 掉。
另外 list available 只列未安装的包，所以已装的包在那里查不到，要看全部得用 dnf list --all。
只留 local 时装带依赖的包会失败：dnf --disablerepo='*' --enablerepo=local install htop 报 nothing provides libhwloc.so.15()(64bit) needed by htop。
这不是本地仓库坏了，而是依赖求解只在「当前启用的仓库集合」里做——hwloc-libs 在 appstream，被你一起关掉了，dnf 就找不到。
所以这条命令的正确用途是证明「某个包确实来自本地仓库」，不适合用来装带依赖的包。要查依赖归属，得把仓库都开回来再问：dnf provides '*/libhwloc.so.15'。

3 · 加一个远程仓库 EPEL 是最常见的例子

RHEL 9 语法
# ① 启用一个已定义的仓库（这一步会真的改 rocky.repo）
dnf config-manager --set-enabled crb
grep -A6 '\[crb\]' /etc/yum.repos.d/rocky.repo

# ② 关回去
dnf config-manager --set-disabled crb

# ③ 从 URL 安装一个「仓库包」（epel 就是这么来的）
dnf config-manager --add-repo https://dl.fedoraproject.org/pub/epel/epel-release-latest-9.noarch.rpm
成功长什么样：① 之后 dnf repolist 多出 crb，且 grep 能看到 crb 段的 enabled=1 已被改写（这就是它与 --enablerepo 的根本区别）；② 之后 crb 又消失；③ 之后 /etc/yum.repos.d/epel.repo 存在。
RHEL 9 的语法变了：老的 dnf config-manager --enablerepo=x 已废弃，现在是 --set-enabled / --set-disabled。照着老教程敲会报 unknown option。
三个长得像的参数，命运完全不同：--enablerepo = 本次临时生效；--set-enabled = 改配置文件、永久；--add-repo = 直接写出一个新的 .repo 文件。

4 · 装 / 卸 / 回滚 把「装错了怎么办」也一起练

install / remove / reinstall
dnf install -y htop
rpm -qa | grep htop
dnf remove -y htop
rpm -qa | grep htop          # 应该没有输出
dnf reinstall -y tree
成功长什么样：install 结尾 Complete!；remove 后 rpm -qa 查不到；reinstall 会先 Reinstalling 再 Cleanup。
remove 会连依赖一起删：卸载被别的包依赖的包时，dnf 提示要删一大串。看清楚列表再按 y，必要时用 dnf remove --noautoremove。
卸载前问自己：这个包是系统自带的吗？删掉 base 组里的东西可能破坏环境。
install 时那两行大小是两层，不是重复：先出现的 4.3 kB 是 repomd.xml（仓库的索引目录），确认「元数据变过了 / 本地没有」之后，才会去拉 44 MB 的 primary / filelists 全量。所以第一次或 dnf clean all 之后一定会看到两行；平时只看到第一行几 kB 才是正常的。
「already installed」和「not installed」都是 info，不是错误：install 一个已经在的包，dnf 输出 Package ... is already installed 加 Nothing to do，退出码仍是 0；remove 一个不存在的包，输出 package xxx is not installed 也不是失败。判断装没装上，只认 rpm -q 的输出，不认这两句话的语气。
考试也常问「怎么撤销」
dnf history
dnf history info last
dnf history undo last
成功长什么样：history 每行一个事务 ID；undo last 输出里把刚才装的东西再删回去，最后多出一条新的 history 记录（撤销本身也是一个事务）。
为什么 undo 不是「删除那条记录」：dnf 不做时光倒流，它是再执行一次反向操作。所以如果这期间文件被手动改过，undo 只负责包层面，不负责你的数据。
versionlock
dnf install -y 'dnf-command(versionlock)'
dnf versionlock add tree
dnf versionlock list
dnf versionlock delete tree
成功长什么样：list 里出现 tree-0:1.8.0-... 这样的行，带 0: 前缀和 epoch。
'dnf-command(versionlock)' 是一种虚拟 provides——用「我需要的能力」而不是包名去装，这在不知道插件包叫什么时特别有用。同类的还有 dnf-command(config-manager)。
provides
dnf provides */semanage
dnf provides /usr/bin/htop
dnf provides '*/nc'
成功长什么样：输出 policycoreutils-python-utils-... : 提供 semanage 这类结果，带 Repo 和 Matched from。

这是本域最该练熟的一条：考试说「安装提供 semanage 命令的包」时，你不需要背包名；真实运维里遇到 command not found，第一反应也应该是它，而不是去搜网页。

5 · 组与模块 RHEL 9 特有的一层

group
dnf group list
dnf group info "Development Tools"
dnf group install -y "Development Tools"
成功长什么样：group list 分「已安装组 / 可用组」两段；group info 列出 Mandatory / Optional 包清单。
组名带空格必须加引号，且大小写要与 group list 输出的完全一致。写错会报 No group marked for installation。
同一软件的多个版本并存
dnf module list nodejs
dnf module enable nodejs:18
dnf module install -y nodejs:18
dnf module list --installed
dnf module reset nodejs
成功长什么样：module list 里每个流有 [d]（默认）/ [e]（已启用）/ [i]（已安装）标记；enable 之后状态变成 [e]。
同一个模块同时只能启用一个流。想换流必须先 dnf module reset nodejs，否则报 Cannot enable ... conflicting requests。
模块和普通包不要混装：模块管理的包用 dnf install 装，后续升级会被模块流限制。
版本差异：RHEL 9 / Rocky 9 仍有 module；RHEL 10 已经移除这套机制。考 EX200（RHEL 9）要会。

6 · 直接处理 rpm 文件 离线场景，以及「dnf 和 rpm 到底差在哪」

关键区别
dnf install -y ./tree-1.8.0-6.el9.x86_64.rpm
rpm -ivh ./tree-1.8.0-6.el9.x86_64.rpm
rpm -Uvh ./tree-1.8.0-7.el9.x86_64.rpm
成功长什么样：dnf install ./x.rpm 会自动去仓库补齐依赖并打印依赖解析结果；rpm -ivh 只打印 Preparing... / Installing...，缺依赖时直接 Failed dependencies 退出。
这是两者的本质区别：dnf = 仓库 + 依赖求解；rpm = 单个文件的事务执行器，不联网、不解依赖。
实践结论：能用 dnf install ./x.rpm 就别用 rpm -ivh；只有确定依赖齐全（或做离线批量）时才用 rpm。
-i vs -U：-i 是安装（已存在会冲突），-U 是升级或安装（已存在则升级）。-F 只升级已装的。
-qf / -ql / -qc / -qi
rpm -qa | grep httpd
rpm -qf /usr/sbin/httpd
rpm -ql httpd | head -20
rpm -qc httpd
rpm -qi httpd
成功长什么样：-qf 反查文件归属；-ql 列出包内全部文件；-qc 只列配置文件；-qi 打印版本、安装时间、签名。
什么时候用哪条：
· 改坏了某个配置，想知道它属于哪个包 → -qf
· 想知道这个包会不会覆盖我的文件 → -ql
· 想只备份该备份的 → -qc
rpm -V
rpm -V httpd
echo $?
成功长什么样：rpm -V 无输出，echo $? 是 0 —— 所有文件与安装时记录一致。
输出里的 9 个字符：S 大小、M 权限、5 摘要、D 设备、L 链接、U 属主、G 属组、T 时间、P 能力。看到 .M....... 就是权限被改过（可能被 chmod 了）。

9 · 附录三：自测 先自己答，再展开

1. 一个装了 100 个 rpm 的目录，为什么 dnf 看不见里面任何包？

因为仓库的入口是 repodata/repomd.xml，不是 rpm 文件本身。没有索引，dnf 不知道目录里有什么、依赖关系如何。createrepo_c 就是生成这份索引的工具。

2. dnf repolist 显示两个仓库都很正常，为什么还可能装不上包？

因为它读的是本地缓存 /var/cache/dnf/，不联网。要证明仓库活着必须 dnf clean all && dnf makecache。「配置读通了」和「仓库可用」是两件事。

3. file:///opt/repo 和 file://opt/repo 差在哪？

前者是本地路径 /opt/repo；后者把 opt 当成主机名，会尝试走网络。本地路径必须三个斜杠。

4. 往本地仓库里新加了几个 rpm，需要做什么？

重新生成索引：createrepo_c --update /opt/localrepo，然后 dnf clean all。不重跑的话，新包在 repodata 里不存在，dnf 依然看不见。

5. 怎么只从一个仓库装包，而不改动任何配置文件？

dnf --disablerepo='*' --enablerepo=local install 包名。命令行参数优先级高于 .repo 的 enabled=，且只对本次生效。

6. 考试说「安装提供 semanage 命令的包」，你怎么找？

dnf provides */semanage。这比记包名（policycoreutils-python-utils）可靠得多，也是遇到 command not found 时的标准动作。

7. dnf install ./x.rpm 和 rpm -ivh ./x.rpm 的本质区别？

dnf 会连仓库、做依赖求解；rpm 只执行单个文件的事务，不解依赖、不联网。缺依赖时 rpm 直接 Failed dependencies。优先用 dnf 装本地包。

8. 装错了包，怎么回退？为什么说 undo 不是「时光倒流」？

dnf history undo last。它实际是再执行一次反向事务，不是删除历史记录；期间被手动改过的文件不会恢复。

9. 为什么 dnf module enable a:1 之后想换 a:2 会失败？

同一个模块同时只能启用一个流。要先 dnf module reset a 再 enable 另一个流。模块流是「整个系统只用这个版本」的承诺。

10. rpm -V 没有输出，说明什么？

说明该包所有文件的校验信息与安装时记录一致，没有被改动。没输出才是好结果——和 mount -a、parted 的成功行为一致。

11. BaseOS 和 AppStream 为什么要分成两个仓库？

BaseOS 放系统底座（内核、glibc、systemd 这类，只有一个版本），AppStream 放应用与多版本组件（可以用 module 选流）。分仓是为了让「底座稳定」和「应用可选版本」互不干扰。

12. 仓库文件里 enabled=0 的仓库，dnf install 会用吗？

不会，除非命令行临时 --enablerepo=那个仓库，或用 dnf config-manager --set-enabled 永久打开。
