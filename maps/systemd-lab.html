0 · 先把「服务」拆成三个维度 不建立这个模型，后面全是死记

考纲只写了一句「启动和停止服务，配置服务以在系统启动时自动启动」，但它背后是三个互相独立的维度。绝大多数错误判断，都是把这三个混成一个「服务开没开」。

维度问的问题查法取值
有没有这个 unit 存不存在systemctl cat X有 / No such file
开机启不启下次开机跑不跑is-enabledenabled / disabled / masked / static
现在跑不跑此刻有没有进程is-activeactive / inactive / failed
is-enabled = enabled+ is-active = active= 正常服务
disabled+ active= 正在跑，但重启后不会自己回来
enabled+ inactive= 设了开机自启，但现在没跑
命令各管一维，互不越界：start / stop / restart 只动进程（影响 is-active）；enable / disable 只动链接（影响 is-enabled）；mask / unmask 封锁的是「还能不能被启动」。

1 · 看清现状（纯只读）一个字节都不要改

is-enabled / is-active
systemctl is-enabled crond sshd firewalld
systemctl is-active  crond sshd firewalld
systemctl status crond --no-pager -l
成功长什么样：is-enabled 三行 enabled；is-active 三行 active；status 头部能读到两行关键信息 —— Loaded: loaded (/usr/lib/systemd/system/crond.service; enabled; preset: enabled) 和 Active: active (running)。
参数别打错：是 --no-pager（不是 --no-paper），是 -l（小写字母 L，不是数字 1）。打错时 systemd 只会甩一句 unrecognized option，不给你任何提示。
preset: 是什么：装机时按厂商策略自动设定的默认值（Rocky/RHEL 一般是 enabled）。它只解释「这个状态是怎么来的」，不影响你现在的操作。
disable 不动进程
ls -l /etc/systemd/system/multi-user.target.wants/crond.service
systemctl disable crond
systemctl is-enabled crond
systemctl is-active  crond
ls -l /etc/systemd/system/multi-user.target.wants/crond.service
成功长什么样：动手前能看到 crond.service -> /usr/lib/systemd/system/crond.service 的软链接；disable 打印 Removed "/etc/systemd/system/multi-user.target.wants/crond.service".；之后是 disabled + active；最后 ls 报 No such file or directory。
disable 只做一件事：删掉 wants/ 目录里那个指向 unit 文件的软链接。它不碰 /usr/lib/systemd/system/crond.service，也不碰正在运行的进程。所以「服务还在跑」和「不自启」同时成立，很正常。
stop 不动自启
systemctl stop crond
systemctl is-enabled crond
systemctl is-active  crond
systemctl start crond
systemctl enable crond
systemctl is-enabled crond; systemctl is-active crond
成功长什么样：stop 之后是 enabled + inactive (dead)，status 里 Main PID 那行消失、出现 Duration: 2d 2h 50min；start 之后 Main PID 换成一个新数字（原来的进程已经退出）；最后两行回到 enabled + active。
只拿 crond 练，不要动 sshd。你是通过 SSH 连进去的，systemctl stop sshd 会当场断开，而且它不会自己回来。
PID 一定会变：start / restart 都是「新建进程」，不是「恢复原进程」。看到 PID 变了不是异常，是必然。
/etc 遮盖 /usr/lib
systemctl mask crond
systemctl is-enabled crond
systemctl enable crond
systemctl start crond
systemctl status crond --no-pager -l | head -6
ls -l /etc/systemd/system/crond.service
成功长什么样：mask 打印 Created symlink /etc/systemd/system/crond.service -> /dev/null.；is-enabled 返回 masked；enable 失败并说 Failed to enable unit: Unit file /etc/systemd/system/crond.service is masked.；start 失败并说 Failed to start crond.service: Unit crond.service is masked.；status 显示 Loaded: masked (Reason: Unit crond.service is masked.) 但 Active: active (running)。
为什么 enable 也会失败：enable 要先读 unit 的 [Install] 段，才知道该往哪个 target 的 wants/ 里建链接。mask 之后这个路径指向 /dev/null，内容是空的，读不到 WantedBy= —— 于是无从下手。顺序只能是 unmask → enable。
两个同名文件，别搞混：/etc/systemd/system/multi-user.target.wants/crond.service 是开机自启的链接；/etc/systemd/system/crond.service 是 mask 的遮盖。在 wants/ 目录里 ls 看到还指向 /usr/lib，不代表 mask 没生效。
mask 不杀进程：正在跑的 crond 依然是 active。mask 只回答「以后还能不能启动它」，不回答「现在要不要停」。日志里会多一条 crond.service: Current command vanished from the unit file —— 这是 systemd 发现 ExecStart= 不见了，只警告、不终止。
wants 链接一直没动
systemctl unmask crond
systemctl is-enabled crond
systemctl is-active crond
ls -l /etc/systemd/system/crond.service
systemctl status crond --no-pager -l | head -4
成功长什么样：unmask 打印 Removed "/etc/systemd/system/crond.service".；随后 enabled + active；ls 报 No such file or directory（遮盖已删）；status 回到 Loaded: loaded (/usr/lib/systemd/system/crond.service; enabled; ...)。
关键：unmask 删的只是 /etc/systemd/system/crond.service -> /dev/null 这个遮盖。wants/ 里的自启链接从 mask 到 unmask 全程没被碰过，所以一揭开就还是 enabled。
list-unit-files vs list-units
systemctl list-unit-files --type=service --no-legend | wc -l
systemctl list-unit-files --type=service --state=enabled --no-legend | wc -l
systemctl list-units  --type=service --state=running --no-legend | wc -l
systemctl list-units  --type=service --all --no-legend | wc -l
成功长什么样：四个数依次约 157 / 23 / 16 / 110（服务装得不一样会浮动，重点是理解口径）。
口径：list-unit-files 数的是磁盘上的 unit 文件（静态视角，含没加载的）；list-units 数的是已经加载进内存的 unit（运行时视角，默认只列 active，--all 才全看）。所以 16 和 23 分属两个集合，本来就不该相等。
★ 这条是今天最坑的一处：list-unit-files --state=running 会输出 0 unit files listed.、stderr 一片空白、退出码 1。因为 running 是 sub-state，list-unit-files 不认；但如果你接了 | wc -l，退出码换成 wc 的 0，你只会看到一个「0」，看着像「没有服务在跑」。
正确做法：--state=running 只配 list-units；要判成败，别接管道。

3 · 自测 先自己答，再展开

1. disable 之后服务还在跑，正常吗？

正常。disable 只删 wants/ 里的软链接，影响的是「下次开机」，不影响当前进程。要停得另外 stop。

2. stop 之后 is-enabled 为什么还是 enabled？

因为 stop 走的是进程控制路径，enable 走的是链接路径，两者根本不通信。

3. mask 之后为什么连 enable 都失败？

enable 需要读 unit 的 [Install] 段才知道往哪建链接；mask 让该路径指向 /dev/null，读不到内容，于是无从下手。必须 unmask 先。

4. unmask 之后为什么直接回到 enabled 而不是 disabled？

因为 wants/ 里的自启链接在 mask 期间从未被删除。unmask 只删掉 /etc/systemd/system/X -> /dev/null 这个遮盖。

5. list-unit-files --state=running 为什么返回 0？

running 是 sub-state，list-unit-files 不接受；它静默返回 0 unit files listed. 并给退出码 1。running 只能配 list-units。

6. static 的服务能 enable 吗？

不能。static 表示 unit 文件里没有 [Install] 段，enable 没有可写的目标，会报 The unit files have no installation config。本机例子：dnf-makecache.service。
