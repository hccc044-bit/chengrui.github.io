今天做了什么

① 开工前核对环境：实验机已连续运行约 5 天，三块盘的布局和 09-18 一致，sdc 仍是整块空盘，今天就用它。

② 从题库 PDF 里抽出存储三题原文，确认这一域只有三道：调整逻辑卷大小、加一个 swap 分区、建卷组与逻辑卷（最后这道考的是 PE 语义）。

③ 只读「看见」三层 —— 这一步一位都没改系统：

读出两件事：rlm 卷组已经把 1791 个 PE 全分光了（VFree 0），所以想让 / 变大只有两条路 —— 往卷组里加盘，或者从别处挪空间。另外 lvs 的 Attr 是 -wi-ao----，那个 o = open，说明 root 和 swap 此刻正被占用。

④ 只建一个 PV，然后自己撤掉：pvcreate /dev/sdc → pvs 看到 VG 列为空、Attr 是 --- → 再跑 pvremove /dev/sdc 恢复干净。这是今天唯一改动系统的操作，可逆正是选它的原因。

⑤ 按「分区优先」重做：给 sdc 建 4 GiB 分区 sdc1（标 lvm）→ pvcreate /dev/sdc1 → pvs 仍是「未入卷组」状态。故意留 ~4.5 GiB 不分区，以后演示「卷组空间用完 → vgextend 加盘」用。

⑥ 做了「从磁盘到 LVM」层级关系图，挂到博客 /maps/lvm.html：磁盘 → 分区 → PV → VG → LV → 文件系统 → 挂载点，七层嵌套，每层标出诞生命令、怎么查、怎么撤，另附三条真实链路对照（有 LVM 的 /、无 LVM 的 /mnt/data、正在做的 /vo）。

⑦ 查清了一件一直没搞懂的事：博客为什么发布失败。 09-18 那次把 hexo clean 和 hexo deploy 放在同一次运行里会 FATAL，站点完全没更新。根因不是网络也不是 git，是批量删除保护：clean 要删掉 public/ 全部文件、deploy 又要清空 .deploy_git，两边删除数累计超过阈值就被拦下。所以换了发布方式 —— 生成后把 public/ 同步到一个镜像目录（只覆盖和新增，几乎不删除），再自己 git push --force。今晚实测通过。

卡住的地方

一、一次给的东西太多，我直接卡住了。

「五层栈 + 扩容两步 + PE 语义 + 三道思考题 + 让你写完整方案」一起上来，我的反馈是「这一块不懂了，从简到难慢一点来」。拆细之后确实管用 —— 今天只做两件事：先看见三层，再建一个 PV，不碰 VG 和 LV。

后来想明白了：我真正卡住的是 PE（「格子」）这个抽象，不是命令。命令看一眼就会敲，但「为什么非要把空间切成等大的格子来记账」这件事没说通，后面所有关于容量的问题就全是乱的。

二、我把 pvs 里的 < 读错了 —— 方向对了一半，对象错了。

看到 pvs 输出 <7.00g，我的判断是「小于 7 GB，被分区表吃掉了一点」。有东西被吃掉这半句是对的，但对象错了：

< 只是显示取整的标记（LVM 只留两位小数，真实值略小就加 <）。而分区表占的空间在分区之外（gpt 表那 17.4 kB 在分区起点之前），所以分区自身的 Size 可以精确等于你输入的 MiB 值。真正被吃掉的是 PV 的标签与元数据区，它计入 PV、不计入 VG —— pvdisplay 的 not usable 一栏能直接看到，实测约 3 MiB。

三、报错看错对象：cannot use 说的是参数，不是设备。

我敲 pvs /dev/sdc1 pvdisplay，报 Cannot use pvdisplay: device not found。第一反应是「设备有问题」，其实是 pvs 只接设备名，我把 pvdisplay 当成第二个设备名传进去了 —— 报错抱怨的是参数解析，不是设备坏了。顺带也确认 pv /dev/sdc 会报 command not found：pv 根本不是 LVM 命令，它是不相干的另一个工具。

今天真正记住的

  • PV / VG / LV 三层做的全是「记账」，实物扇区一点没动。 pvcreate = 登记设备；vgcreate = 把空间切成等大 PE 格子记下来；lvcreate = 从账上划走 n 格。这句话通了之后，PE 就不抽象了。
  • 账本是自洽的：VG Size = PE Size × Total PE。 实测 4 MiB × 1791 = 7164 MiB ≈ <7.00 GiB，和 vgs 里的 VSize 对得上。LV 的大小必须是 PE 的整数倍 —— 这才是「50 个扩展单元 × 16 MiB」那题的考点（16 × 50 = 800 MiB，出题人偏不写 800）。
  • PV 和 VG 是两层，不是一回事。 pvs 的 VG 列为空 = 这个 PV 还没被任何卷组认领；Attr 的 a = allocatable，没入伙时显示 ---。一个 PV 可以独立存在，一个 VG 可以吃掉多个 PV —— 这正是 vgextend 加盘扩容能成立的原因。
  • ★ 扩容永远是两个动作。 lvextend 只改 LVM 层的账，文件系统层不知道 —— 扩完会停在「LV 300 MiB / 文件系统仍是 200 MiB」的错位状态，df 一点不变，中间那 100 MiB 白白闲置。必须再补一条 xfs_growfs（xfs）或 resize2fs（ext4）。这也解释了参考解里 lvextend 之后为什么插一条 blkid：先确认文件系统类型，才知道该用哪个 grow 命令。
  • 先分区再 pvcreate，比整盘直接做更好。 三个理由：分区能标 lvm 类型给人看、同一块盘能只切一部分给 LVM（swap 分区就是这么和 LVM 共存的）、想反悔时直接 pvremove 就能回头（整盘做了 PV 想再分区得先 pvremove + wipefs）。例外是专用数据盘，整盘做也完全正常。但要记住分区不是 LVM 的一层，只是设备层的准备动作 —— LVM 只要求「给我一个块设备」。
  • xfs 只能扩不能缩（要缩只能重建）；ext4 能缩但必须先卸载。

② 两轮问答里挖出来的机制

  • 2 TiB 是 msdos 的上限，不是 gpt 的。 MBR 用 4 字节存 LBA → 2³² × 512B = 2 TiB；gpt 用 8 字节。我一开始把这个数字记到了 gpt 头上，方向记反了。
  • 写进 fstab 就是「自动挂载」，没有别的魔法。 开机时 systemd 读 fstab、为每条生成 .mount 单元；桌面插 U 盘会自动出现在 /run/media，那是 udisks2 干的，服务器环境里没有这层兜底。
  • parted 显示用十进制、输入用二进制。 输入 1MiB → 1025MiB，print 出来是 1049kB → 1075MB，差 1074MB。数字没错，是尺子换了一把（1024 MiB = 1073.74 MB）。
  • primary 在 gpt 盘上没有类型含义，只会被存成分区名 —— 证据就在自己的输出里：msdos 盘 print 的列名是 Type，gpt 盘是 Name，blkid 输出里出现 PARTLABEL="primary"。
  • fstab 第 5、6 字段：5 = dump 标志（工具早淘汰了，恒写 0）；6 = fsck 顺序，只有 0/1/2 三个合法值，1 是根分区专属。

卡住的地方

一、动手前和动手后，我用的是同一批命令 —— 层序错了。

被问「mkfs 之前用什么命令确认目标设备」，我答 wipefs / blkid。工具没错，但这两个验的是「这块盘上现在有什么签名」，那是流程最后一环的事后验证，不是动手前的确认。动手前该看的是 lsblk -f 和 parted print free —— 一个是内核实时状态，一个是分区表里究竟记了什么。

这是我的「验收命令只验某一层」的第八次，而且这次是层序错：把事后验证当成了事前确认。

二、我以为写错设备名会「静默挂错盘」，实际是开不了机。

我原来的判断是「盘名对调了就挂错盘，而且不会报错，会一直以为挂载成功」。真实后果严重得多：/dev/sdb1 这个名字指向另一块盘，若那上面没有 sdb1 分区 → 设备根本不存在 → 挂载失败；fstab 条目挂载失败且没加 nofail 时，systemd 的 local-fs.target 跟着失败 → 整机掉进 emergency mode，SSH 都连不上，得进控制台把那行注释掉才能开机。

所以后果不是「少挂一个目录」，是「开不了机」。nofail 和 x-systemd.device-timeout= 就是为这个存在的（生产上写非关键挂载常用，考试要求持久化的题不加）。

三、findmnt --verify 和 mount -a 是两个层，而且验之前必须先 umount。

findmnt --verify 是静态检查：语法、字段合法性、挂载点是否存在、选项是否被支持 —— 但不做实际挂载，所以 UUID 写错它照样报 Success。umount && mount -a 才是动态走一遍开机流程。语法合法 ≠ 挂得上，挂得上 ≠ 语法没问题，两个都要做。

还有个前提我一开始没想到：必须先 umount。因为 mount -a 判断「要不要挂」看的是挂载点是否已经出现在挂载树里，手工挂载的残留会让它直接跳过 —— 一条 fstab 都没读到，等于什么都没验。

四、重复标题会让锚点悄悄漂移。

### 今天做了什么 在一篇里出现 4 次，Hexo 把它们编成 今天做了什么、今天做了什么-1、今天做了什么-2、今天做了什么-3。这本身不算错，但意味着：只要往中间插一天，后面所有编号全部平移。任何指向「某天做了什么」的链接，第二天就可能指到别处。

这不是美观问题，是链接不可引用。改法是把日志按天分节（## 2026-09-18 星期五 这种标题天然唯一），一天之内只用加粗小标题，不再产生重复标题。

五、我以为是「目录更紧凑」的开关，其实是另一回事。

我原本打算打开 toc.style_simple，理由是「长文章目录更紧凑」。去主题源码里看了一眼才发现：它实际的效果是侧边栏只保留目录，把作者卡、公告卡、最新文章卡全部不渲染，跟「紧凑」没关系。

结论是这个开关不开。顺带又一次印证了老毛病 —— 我以为的那个对象，和系统里实际的那个对象，不是同一个。

六、拿「运行时才生成的值」去查「静态文件」，等于什么都没验。

我加完节点标识之后，先去线上 HTML 里搜 data-nid 的取值，没搜到就以为没部署上去。实际上 data-nid 是页面加载后由 JS 渲染出来的 —— 静态 HTML 里根本没有这个字符串，只有生成它的那段代码。

这又是「验收命令只验某一层」的一个新变种，而且这次是反的：前几次是验得太浅（配置读通就当事情做成），这次是查错了对象（去静态文件里找运行时的值）。正确的做法是把线上那份 HTML 抓下来、真的跑一遍 JS 再看 DOM。

七、重复的标题会让标识撞车。

三个还没展开的章节里，各有一个占位节点标题都叫「本节将要覆盖的能力」—— 派生出同一个节点标识。链接指过去只会落到第一章，而且是静默落错。改成撞车时按所属章节加后缀（本节将要覆盖的能力-sys）才唯一。

这个坑是我自己写的自测用例抓出来的，肉眼完全看不出来 —— 47 个节点里有 2 个撞车，看上去一切正常。

我用 ls -ld /home/managers 去验「非成员进不去」，跑出来退出码 0，看着像她能进。实测才搞明白：

ls -ld 只对路径做一次 stat()，而 stat 只需要路径上每一级父目录的 x，对目标对象自己的权限一位都不要。

命令 实际在问什么 非成员退出码
ls -ld /home/managers 只 stat 这个对象 0 ← 骗人的
ls /home/managers 读目录内容，要目录的 r 2
cd /home/managers 进目录，要目录的 x 1
touch /home/managers/zz 建条目，要目录的 wx 1

口诀：想验什么动作，就敲那个动作本身；stat 类命令（ls -ld / ls -l / test -r）都不能代替。

二、blkid 有输出 ≠ 有文件系统。

我原来的判据是「有输出就是格式化过了」，错：

输出里的字段分两类：TYPE= / UUID= 是文件系统的属性；PARTUUID= / PARTLABEL= 只是分区表的属性。判据要改成看 TYPE= 字段，不是看有没有输出。

三、SGID 只管一半：它管属组，不管权限位。

协作目录那题，SGID 一开，natasha 建的文件属组确实是 sysmgrs 了，但文件自己是 -rw-r--r--，组位只有 r —— 组里其他人照样改不了，协作没实现。

新建文件的权限位由 umask 决定（022 → 644），SGID 碰不到它。要「组员能互相改文件」，必须再补一层默认 ACL。

四、默认 ACL 会接管 umask。

目录 令 umask 077 后新建的文件
有默认 ACL -rw-rw----+ ← umask 完全没生效
无默认 ACL -rw-------. ← umask 正常生效

六、我记错的一个点：ACL 组类不是「命中即止」，是并集。

我原来记的模型是「属主 → 具名用户 → 属组 → 其他，命中即止」。实测被推翻：

正确的判定是：

今天真正记住的判断

  • 「未验证」比「不会」更危险。 今天三次出错，没有一次是命令敲错，全是验收只做了一半。以后每条验收命令都先问一句：它验的是「配置读通了」，还是「事情做成了」？

  • ACL 的判定是「命中即止」，不是层层叠加。 属主 → 具名用户 → 属组/具名组 → 其他用户，命中第一个就结束。所以「其他用户给了读、但某个具名用户要求不能读」并不矛盾 —— 他在第二步就被截停了，根本走不到最后。

  • mask 是具名条目的天花板。 具名用户的真实权限 = 自己的条目 ∩ mask。

  • chmod 的数字写法一定会重写 mask，符号写法只动你点名的位。 有 ACL 的文件上敲 chmod 644，是把中间那一位数字写进 mask，可能悄悄砍掉具名用户的权限；chmod o=r 只改其他用户，mask 原地不动。我原先说「chmod 必须在 setfacl 之前」太绝对了 —— 真正的判据是 chmod 之后 mask 够不够用。

  • 有扩展 ACL 的文件，ls -l 中间那三位显示的是 mask，不是属组权限。 看着像 664，实际可能完全不是，只看 ls -l 会误判。

  • root 不能当验收工具。 把文件权限设成 000，root 读它照样返回成功（它有 CAP_DAC_OVERRIDE，权限位对它不生效）。必须换一个没有特权的身份去验。

先搞清了一个本质：NAT 模式下虚拟机连的不是物理网络，而是 VMware 虚拟出来的一台「隐形路由器」（VMnet8）。它有固定的三个约定：

地址 归属
.1 宿主机上的 VMnet8 虚拟网卡
.2 NAT 网关，整个虚拟网络唯一的出口
.128–.254 VMware 自带的 DHCP 地址池

所以改网段相当于把这台路由器搬到了另一个小区 —— 宿主机侧和虚拟机侧必须同时跟上，少一侧就断网。

排查是在宿主机侧直接读权威配置完成的：VMware 的虚拟网络配置是纯文本，就在 C:\ProgramData\VMware\ 下（vmnetnat.conf / vmnetdhcp.conf），比在图形界面里翻要直接。另外宿主机上 arp -a 能一眼看出虚拟机的真实 IP，比进虚拟机敲命令还快。

几条今天真正记住的判断

  • 网关是谁是「被指定」的，不是靠习惯推出来的。 我下意识觉得网关就是本网段第一个可用地址（.1），但 VMware 把 .1 给了宿主机网卡、.2 给了 NAT 设备。真实网络里网关是谁，只能查设计文档或问规划者。
  • ping 同网段的地址根本不经过网关。 两台同 /24 的机器互 ping 靠的是直接 ARP，路由表和默认网关完全不参与 —— 所以「ping 不通网关」这个说法本身就不准确，它真正的含义是二层 ARP 不通。
  • 双向都不通 = 链路层问题；只有一个方向不通 = 防火墙。 今天宿主机能 ping 通虚拟机、虚拟机 ping 不通宿主机，顺着这条推，问题就在宿主机 Windows 防火墙（VMnet8 被 Windows 归为「公用网络」，默认不响应入站 ping）。这是个假问题，不影响上网，和真问题叠在一起，一开始被混为一谈了。
  • 官方文档也可能是为旧大版本写的。 阿里云镜像页给的命令用的是 Rocky-*.repo，那是 Rocky 8 的命名，在 Rocky 9 上要么完全不生效、要么只静默改一半。照抄任何 glob 之前，先 ls 核对本机真实文件名。
  • setenforce 0 临时判断故障是正常手段，永久 disabled 不是。 一旦 disabled 并重启过，想恢复就得 touch /.autorelabel 做全盘 relabel。幸好我是在重启之前改回来的，一条 setenforce 1 就完事，零副作用 —— 这个「还没重启」的窗口很值钱。
  • 判断「某事有没有做过」，不能只看我以为的那个位置。 比如备份，我以为会在某个目录、没看到就以为没做，实际人家用的是另一个位置。要先搜索，多路径找一遍，再下结论。

2026-09-11 星期五

今天做了什么

把 RHCE 和 CKA 两个证的备考方向定下来了，顺手把能查到的官方大纲核对了一遍，发现三个和网上老攻略不一样的地方。

三个关键发现

  1. RHCE 有前置证书。 可以直接报名 EX294，但红帽规定必须同时持有有效的 RHCSA（EX200）才会授予 RHCE 称号。所以真实路径是 RHCSA → RHCE，跳不过去。
  2. RHCE 新版已经改名并加考。 RHEL 10 版本的官方名称改成了「Red Hat Certified Advanced System Administrator in Ansible」，新增 ansible-navigator、VS Code 工作流、Git 基本操作三项考点。网上大量老资料不覆盖这部分，不能照老攻略学。
  3. RHCE 有个隐藏评分点：配置必须在重启后仍然生效。 服务、挂载、防火墙、用户，只要 reboot 后失效就是零分。这是最高频的失分原因。

CKA 的分数分布（决定复习时间怎么分配）

考点域 权重
Troubleshooting 故障排查 30%
Cluster Architecture 集群架构与安装 25%
Services & Networking 服务与网络 20%
Workloads & Scheduling 工作负载与调度 15%
Storage 存储 10%

Troubleshooting 独占 30%，是最重的部分，也是唯一能靠练习真正拉开差距的地方。

两个考试的共同点（决定了学法）

  • 都是 100% 纯实操，全程在真实环境里敲命令，一道选择题都没有。
  • 考试环境不提供互联网：RHCE 只能查考场内的产品文档，CKA 只能查 kubernetes.io/docs。
  • 推论：凡是「需要搜一下才知道怎么写」的内容，就等于不会。 必须练到能默写。
